# 任务队列与处理

> 本文档梳理 MinerU 天枢的任务生命周期：从上传入队，到 Worker 原子领取、引擎处理，再到结果落盘与回收。涉及核心文件 [api_server.py](../backend/api_server.py)、[task_db.py](../backend/task_db.py)、[litserve_worker.py](../backend/litserve_worker.py)、[task_scheduler.py](../backend/task_scheduler.py)、[redis_queue.py](../backend/redis_queue.py)。

## 1. 三个后台进程

由 [start_all.py](../backend/start_all.py) 在同一进程组中拉起，构成完整流水线：

| 进程 | 文件 | 端口 | 职责 |
|------|------|------|------|
| **API Server** | [api_server.py](../backend/api_server.py) | 8000 | 接收上传、写入源文件、向 SQLite 插入 `pending` 任务、对外提供查询/结果服务 |
| **LitServe Worker 池** | [litserve_worker.py](../backend/litserve_worker.py) | 8001 | GPU 解析主力。主动循环拉取任务、原子领取、路由引擎、回写结果 |
| **Task Scheduler** | [task_scheduler.py](../backend/task_scheduler.py) | — | 监控队列、健康检查、重置超时任务、清理过期结果文件 |
| MCP Server（可选）| [mcp_server.py](../backend/mcp_server.py) | 8002 | 供 AI 助手通过 Model Context Protocol 远程调用 |

启动顺序：API（等 3s）→ Worker（等 5s）→ Scheduler（`--wait-for-workers`）→ MCP（可选）。任一进程意外退出，`launcher.wait()` 会停掉全部服务（[start_all.py:268](../backend/start_all.py#L268)）。

## 2. 任务的一生

```
用户上传
  │  POST /api/v1/tasks/submit  (api_server.py:215)
  ▼
写源文件到 UPLOAD_DIR(input/)，db.create_task() 插入 tasks 表 status='pending'
  │  (task_db.py:154)  ── 若启用 Redis，同时 enqueue 到优先级队列
  ▼
Worker 循环 _worker_loop() 调用 get_next_task() 原子领取  (litserve_worker.py:346)
  │  BEGIN IMMEDIATE + UPDATE ... WHERE status='pending'  (task_db.py:201)
  ▼
status='processing'，_process_task() 路由引擎处理  (litserve_worker.py:384)
  ▼
update_task_status(status='completed', result_path=..., data=...)  (task_db.py:326)
  │  data 字段存 pdf_path / json_content / markdown，供前端双向定位
  ▼
用户轮询 GET /api/v1/tasks/{task_id} 取结果
  ▼
Scheduler 在 N 天后清理结果文件与记录  (task_scheduler.py:174)
```

### 状态机

`tasks.status` 取值与流转：

| 状态 | 含义 | 进入方式 |
|------|------|----------|
| `pending` | 排队中 | 创建任务 / 重试 / 恢复 / 重置超时 |
| `processing` | 处理中 | Worker 原子领取 |
| `completed` | 成功 | 引擎产出结果并回写 |
| `failed` | 失败 | 引擎抛异常 / 子任务失败连带父任务 |
| `paused` | 已暂停 | 仅允许从 `pending` 暂停 |
| `cancelled` | 已取消 | 用户取消 |

状态更新均带 **乐观条件**（如 `WHERE status='processing' AND worker_id=?`），防止跨 Worker 误写（[task_db.py:342](../backend/task_db.py#L342)）。

## 3. 队列实现：SQLite + 可选 Redis（Hybrid Queue）

天枢采用混合队列：**SQLite 永远是元数据/历史/结果的权威存储**；Redis 是可选的高性能队列层，用来绕开 SQLite 单写锁瓶颈。

### 3.1 SQLite 原子领取（默认）

并发安全的核心在 [`get_next_task()`](../backend/task_db.py#L201)：

```python
cursor.execute("BEGIN IMMEDIATE")            # 立即获取写锁
cursor.execute("SELECT * FROM tasks WHERE status='pending' "
               "ORDER BY priority DESC, created_at ASC LIMIT 1")
cursor.execute("UPDATE tasks SET status='processing', worker_id=? "
               "WHERE task_id=? AND status='pending'")
if cursor.rowcount == 0:   # 被别的 Worker 抢走了，重试
    continue
```

- `BEGIN IMMEDIATE` + 带 `status='pending'` 条件的 `UPDATE` 保证 **同一任务只会被一个 Worker 领走**，多 Worker 安全无重复处理。
- 抢占失败自动重试，最多 `max_retries=3` 次。
- 连接策略：每次操作新建连接、用完即关（`check_same_thread=False`、`timeout=30s`），不使用连接池避免跨线程共享（[task_db.py:65](../backend/task_db.py#L65)）。

排序规则：**优先级降序 + 创建时间升序**（`priority DESC, created_at ASC`），priority 数字越大越先处理。

### 3.2 Redis 优先级队列（可选）

由环境变量 `REDIS_QUEUE_ENABLED=true` 开启（[redis_queue.py:437](../backend/redis_queue.py#L437)）。实现见 [`RedisTaskQueue`](../backend/redis_queue.py#L65)：

- **优先级队列**用 Sorted Set，score = `-priority * 1e10 + timestamp`，`BZPOPMIN` 阻塞取最高优先级任务。
- **可靠投递**：任务从队列移入 `processing` Hash（带 `worker_id` + `claimed_at`），完成时 `complete()` 移除，失败时 `fail()` 可选 `requeue`。
- **超时恢复**：`recover_stale_tasks()` 扫描 `processing` 中超过可见性超时（默认 300s）的任务重新入队。
- **优雅降级**：`get_redis_queue()` 单例；若 Redis 未启用/不可用，标记为 `False`，全部回退到 SQLite 轮询，业务无感知（[redis_queue.py:417](../backend/redis_queue.py#L417)）。

即便启用 Redis，任务完整数据仍从 SQLite 读取（Redis 只存 task_id 与轻量元数据），状态最终也回写 SQLite（[task_db.py:277](../backend/task_db.py#L277)）。

## 4. Worker 主动循环模式

每个 GPU 进程 `setup()` 时启动一个守护线程跑 [`_worker_loop()`](../backend/litserve_worker.py#L346)：

```
while running:
    task = task_db.get_next_task(worker_id)
    if task:  _process_task(task)
    else:     time.sleep(poll_interval)   # 默认 0.5s
```

- Worker **主动拉取**，不依赖 Scheduler 触发。Scheduler 仅做监控/兜底。
- 也保留被动模式：`predict({"action":"poll"})` 可手动触发一次拉取（自动循环开启时会跳过）。
- **并发控制**：`MAX_CONCURRENT_TASKS`（默认 1）= `workers_per_device`，强制每 GPU 串行处理，防止爆显存（[litserve_worker.py:1089](../backend/litserve_worker.py#L1089)）。
- Worker 标识：`tianshu-{hostname}-{device}-{pid}`，CUDA 隔离通过 `CUDA_VISIBLE_DEVICES` 按设备绑定。

## 5. 引擎路由（`_process_task`）

[`_process_task()`](../backend/litserve_worker.py#L384) 按 `backend` 选项 + 文件扩展名分派，处理顺序：

1. **vLLM 容器互斥切换**：`paddleocr-vl-vllm` 启 paddle 容器停 mineru 容器；`vlm-auto-engine`/`hybrid-auto-engine` 反之（详见模型部署文档）。
2. **Office 预处理**：`.docx/.xlsx/.pptx/.doc/.xls/.ppt` 且 `convert_office_to_pdf=true` 时先用 LibreOffice 转 PDF。
3. **PDF 拆分**：大 PDF（默认 >500 页）拆成子任务并行处理（见第 6 节）。
4. **去水印**：PDF + `remove_watermark=true` 走 YOLO11x + LaMa 预处理。
5. **引擎分派**：
   - `sensevoice` → 音频引擎
   - `video` → 视频引擎
   - `paddleocr-vl` / `paddleocr-vl-vllm` → PaddleOCR-VL（本地 / vLLM）
   - `pipeline` / `vlm-*` / `hybrid-*` → MinerU
   - `auto` → 按扩展名自动选择（格式引擎 / 音视频 / MinerU / MarkItDown 兜底）
   - 其它 → 查 `FormatEngineRegistry`（FASTA/GenBank 等）
6. **回写结果**：`update_task_status(completed, ...)` 写入 `result_path` 与 `data`（含 `pdf_path`、`json_content`、`markdown`）。
7. **子任务合并**（如果是子任务）。

详细的各引擎解析方法见《[各种文件的解析方法](./02-文件解析方法.md)》。

## 6. 父子任务系统（大 PDF 拆分）

由 `PDF_SPLIT_*` 环境变量控制（[litserve_worker.py:864](../backend/litserve_worker.py#L864)）：

| 变量 | 默认 | 含义 |
|------|------|------|
| `PDF_SPLIT_ENABLED` | `true` | 是否启用拆分 |
| `PDF_SPLIT_THRESHOLD_PAGES` | `500` | 超过该页数才拆分 |
| `PDF_SPLIT_CHUNK_SIZE` | `500` | 每个子任务的页数 |

流程：
1. `convert_to_parent_task()` 把原任务转为父任务（[task_db.py:628](../backend/task_db.py#L628)）。
2. `split_pdf_file()` 切片，每片 `create_child_task()` 创建子任务，`options.chunk_info` 记录 `start_page/end_page`。
3. 子任务被各 Worker 并行领取处理（与普通任务无异）。
4. 每个子任务完成回调 `on_child_task_completed()`，累加 `child_completed`；当 `child_completed >= child_count` 时触发父任务合并（[task_db.py:687](../backend/task_db.py#L687)）。
5. `_merge_parent_task_results()` 按 `start_page` 排序，拼接各片 `result.md`、按页码偏移修正 `page_idx` 合并 `result.json`，再 `normalize_output()`，清理子任务临时文件（[litserve_worker.py:905](../backend/litserve_worker.py#L905)）。
6. 任一子任务失败 → `on_child_task_failed()` 连带把父任务标记 `failed`。

## 7. Scheduler 的兜底职责

[task_scheduler.py](../backend/task_scheduler.py) 在 Worker 自动循环模式下只做轻量监控：

| 任务 | 默认间隔 | 实现 |
|------|----------|------|
| 队列状态监控 | 300s（5 分钟） | `get_queue_stats()` |
| Worker 健康检查 | 900s（15 分钟） | GET `/health` 兜底 POST `/predict` |
| 重置超时任务 | 60 分钟 | `reset_stale_tasks()`：`processing` 超时 → `pending`，`retry_count+1`（[task_db.py:559](../backend/task_db.py#L559)） |
| 清理过期结果 | 每 24 小时 | `cleanup_old_task_records(days=7)`：删文件 + 删记录（[task_db.py:529](../backend/task_db.py#L529)） |

## 8. 任务管理 API

提交：`POST /api/v1/tasks/submit`（[api_server.py:215](../backend/api_server.py#L215)），表单字段含 `file`、`backend`、`lang`、`priority` 及各引擎选项（详见解析方法文档）。

其余端点（[api_server.py](../backend/api_server.py)）：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/tasks/{task_id}` | 查询任务详情/结果 |
| POST | `/api/v1/tasks/{task_id}/cancel` | 取消任务（pending/processing/paused → cancelled，**保留记录与文件**） |
| DELETE | `/api/v1/tasks/{task_id}` | **彻底删除**任务（物理删除文件 + 数据库记录，不可恢复） |
| DELETE | `/api/v1/tasks/failed/clear` | 一键清理所有失败任务 |
| POST | `/api/v1/tasks/{task_id}/retry` | 重试（重置为 pending，retry_count+1） |
| POST | `/api/v1/tasks/{task_id}/pause` | 暂停（仅 pending） |
| POST | `/api/v1/tasks/{task_id}/resume` | 恢复（paused → pending） |
| POST | `/api/v1/tasks/{task_id}/clear-cache` | 清缓存（保留记录） |
| GET | `/api/v1/queue/stats` | 队列统计 |
| GET | `/api/v1/queue/tasks` | 任务列表（可按 backend/status 筛选） |
| POST | `/api/v1/admin/cleanup` | 手动清理旧任务 |
| POST | `/api/v1/admin/reset-stale` | 手动重置超时任务 |
| GET | `/api/v1/engines` | 列出可用引擎 |
| GET | `/api/v1/health` | 健康检查 |
| GET | `/api/v1/files/output/{path}` | 结果文件服务 |
| GET | `/api/v1/files/upload/{path}` | 源文件服务 |

所有任务接口受 JWT 鉴权保护（`require_permission`），默认账号 `admin / admin123`。

## 9. 数据表结构

`tasks` 表（[task_db.py:97](../backend/task_db.py#L97)），首次初始化自动建表并做增量迁移（parent-child 字段、`user_id`、`data`）：

| 字段 | 说明 |
|------|------|
| `task_id` | UUID 主键 |
| `file_name` / `file_path` | 原文件名 / 源文件磁盘路径 |
| `status` / `priority` / `backend` / `options` | 状态 / 优先级 / 引擎 / JSON 选项 |
| `result_path` / `error_message` | 结果目录 / 错误信息 |
| `created_at` / `started_at` / `completed_at` | 时间戳 |
| `worker_id` / `retry_count` | 处理 Worker / 重试次数 |
| `parent_task_id` / `is_parent` / `child_count` / `child_completed` | 父子任务 |
| `user_id` | 提交用户 |
| `data` | 扩展元数据 JSON（`pdf_path`、`json_content`、`markdown`，供前端双向定位/预览） |

索引：`status`、`priority DESC`、`created_at`、`worker_id`、`parent_task_id`、`is_parent`。
