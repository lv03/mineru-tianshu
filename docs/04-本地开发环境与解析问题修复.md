# 04 · 本地开发环境与解析问题修复

本文记录一轮针对**本地原生开发**（非 Docker，Mac/CPU 常见路径）的修复，覆盖四个问题：

1. 原生启动时模型不走 `backend/model`
2. MinerU pipeline 模型路径拼接出错（`models/models/` → `HFValidationError`）
3. 「双向定位」视图一排空框（取不到文字）
4. 左侧 PDF 源文档预览空白
5. 「双向定位」高亮框严重偏移

> 适用范围：通过 `python backend/start_all.py` 启动的原生开发环境。Docker 各服务有独立 `command` + entrypoint，**不经过 `start_all.py`**，故以下后端注入逻辑不影响 Docker。

---

## 1 · 原生启动使用 `backend/model` 下的本地模型

### 症状
原生启动后，各引擎报「本地模型缺失」，或仍尝试联网下载。

### 根因
各引擎代码里的默认路径指向的是**容器路径**，在 Mac/原生环境并不存在：

| 引擎 | 代码默认路径 | 读取的环境变量 |
|------|--------------|----------------|
| SenseVoice / Paraformer | `/app/models/...` | `MODEL_PATH`（默认 `/app/models`） |
| 水印 YOLO | `/app/models/YOLO11/best.pt` | `MODEL_PATH` |
| PaddleOCR-VL | `/root/.paddlex/official_models/...` | **`PADDLEX_HOME`**（默认 `/root/.paddlex`，非 `MODEL_PATH`） |
| MinerU | 读 `~/mineru.json`，内容写死 `/app/models/...` | `MINERU_MODEL_SOURCE` + `MINERU_TOOLS_CONFIG_JSON` |

此外 worker 会根据 `MODEL_DOWNLOAD_SOURCE` 反推 `MINERU_MODEL_SOURCE`，而 `backend/.env` 原为 `auto` → MinerU 走联网下载。

### 修复
- [`backend/start_all.py`](../backend/start_all.py)：新增 `configure_local_models()`，在加载 `.env` 之后、拉起子进程之前注入：
  - `MODEL_PATH` = `<repo>/backend/model`
  - `PADDLEX_HOME` = `<repo>/backend/model/paddlex_cache`
  - 生成 `backend/model/mineru.local.json`（宿主机绝对路径），并设 `MINERU_TOOLS_CONFIG_JSON` 指向它
  - 均用 `setdefault`，保留手动覆盖能力
- [`backend/.env`](../backend/.env)：`MODEL_DOWNLOAD_SOURCE=local`、`HF_OFFLINE=1`

> MinerU 配置定位机制：`MINERU_TOOLS_CONFIG_JSON`（绝对路径）→ 否则 `~/mineru.json`；`MINERU_MODEL_SOURCE=local` 时从其中读 `models-dir.pipeline` / `models-dir.vlm`。

## 2 · MinerU pipeline 模型路径拼接出错

### 症状
```
HFValidationError: Repo id must be in the form 'repo_name' or 'namespace/repo_name':
'.../PDF-Extract-Kit-1.0/models/models/MFR/unimernet_hf_small_2503'
```
注意路径里有重复的 `models/models/`。

### 根因
MinerU 3.0 的 pipeline 相对路径常量**本身已含 `models/`**（`mineru/utils/enum_class.py`）：
```python
unimernet_small = "models/MFR/unimernet_hf_small_2503"
```
调用处会 `os.path.join(root, "models/MFR/...")`（`mineru/backend/pipeline/model_init.py`）。
因此 pipeline 根应到 `PDF-Extract-Kit-1.0` 这一层。若误写成 `.../PDF-Extract-Kit-1.0/models`，拼接后变成 `models/models/...`，目录不存在 → MinerU 回退把绝对路径当 HF repo id → 报错。

### 修复
[`backend/start_all.py`](../backend/start_all.py) 生成配置时，pipeline 根 = `model_root / "PDF-Extract-Kit-1.0"`（去掉多余的 `/models`）：
```json
{
    "models-dir": {
        "pipeline": ".../backend/model/PDF-Extract-Kit-1.0",
        "vlm":      ".../backend/model/MinerU2.5-Pro-2605-1.2B"
    },
    "config_version": "1.3.1"
}
```

> ⚠️ **遗留**：同样的 `/models` 多余层级仍存在于 [`backend/download_models.py`](../backend/download_models.py)（生成 Docker 用 `mineru.json` 的逻辑）与仓库自带的 `backend/model/mineru.json`。升级到 MinerU 3.0.9 后，Docker 跑 pipeline 会踩同样的坑，待统一修正。

## 3 · 双向定位视图「一排空框」

### 症状
右侧「双向定位」渲染出多个框，但每个框**没有文字**；左侧无 PDF。

### 根因
[`backend/output_normalizer/standard_output_normalizer.py`](../backend/output_normalizer/standard_output_normalizer.py) 选「主 JSON」时用条件 `"result" in f.name`。MinerU pipeline 在 `auto/` 下产出 4 个同前缀文件：

| 文件 | 内容 | 是否含文字 |
|------|------|-----------|
| `result.pdf_model.json` | 仅版面检测框（cls_id/label/score/bbox） | ❌ |
| `result.pdf_middle.json` | 中间结果 | ❌（结构不适合展示） |
| `result.pdf_content_list.json` | v1 结构化内容 | ✅ |
| `result.pdf_content_list_v2.json` | v2 结构化内容 | ✅ |

`"result" in f.name` 对 4 个全部命中，`for…break` 取 rglob 第一个，常误选 `model.json`（无文字）→ 前端按页/版面块渲染出空框。

### 修复
改为按优先级显式打分：`content_list_v2 > content_list > content/result`，并**排除 `_model.json` / `_middle.json`**；无内容列表时退取最大的非 model/middle 文件。

## 4 · 左侧 PDF 源文档预览空白

### 症状
右侧文字正常，但左侧「源文档预览」空白。

### 根因
`--output-dir` 默认是相对路径 `./mineru_tianshu_output`，导致数据库里 `result_path` 存为**相对路径**；而 API 的 `OUTPUT_DIR` 是 `.resolve()` 后的**绝对路径**。
计算预览链接时 `preview_pdf.relative_to(OUTPUT_DIR)` 拿相对路径比绝对路径 → 抛 `ValueError`，被 `except: pass` 吞掉 → `pdf_path` 未设置。
（Markdown/JSON 不受影响，因为它们直接用相对 `result_dir` 读取，相对当前工作目录 `backend/` 能命中。）

### 修复
- [`backend/api_server.py`](../backend/api_server.py)：`preview_pdf.relative_to(...)` → `preview_pdf.resolve().relative_to(...)`，先转绝对再求相对。**对已存在任务即时生效，无需重跑。**
- [`backend/start_all.py`](../backend/start_all.py)：`args.output_dir` 启动时 `Path(...).resolve()` 成绝对路径，让 worker 写入与 API 读取路径一致，从根上杜绝。

## 5 · 双向定位高亮框严重偏移

### 症状
点击右侧块能在左侧 PDF 定位，但高亮框被放大并右移，与实际文字错位。

### 根因
MinerU content_list_v2 的 bbox **逐轴归一化到 [0,1000]**（pipeline 与 vlm 一致，见 `mineru/backend/*/＊_middle_json_mkcontent.py`）：
```python
int(x0 * 1000 / page_width),  int(y0 * 1000 / page_height),
int(x1 * 1000 / page_width),  int(y1 * 1000 / page_height),
```
真实数据交叉验证（letter 页 612×792）：x 比例恒为 `1000/612≈1.63`、y 比例恒为 `1000/792≈1.26`。

前端有两个错误：
1. 用「该页所有块的最大右边缘 x1」推断页宽，得到的是**内容最右缘**（如 887），比真实基准 1000 小 → scale 偏大 → 框放大右移。
2. x、y 共用同一个 scale；但归一化按轴独立进行（不保持纵横比），x/y 比例本就不同。

### 修复
- [`frontend/src/views/TaskDetail.vue`](../frontend/src/views/TaskDetail.vue)：识别到 v2 嵌套格式（`[[page0_blocks], ...]`）时，给 block 标注归一化基准 `_page_width = _page_height = 1000`，并透传 `_page_height`。
- [`frontend/src/components/VirtualPdfViewer.vue`](../frontend/src/components/VirtualPdfViewer.vue)：`pageOcrScales` 改为返回独立的 `{ sx, sy }`；`getBlockStyle` 与滚动定位分别用 `sx` / `sy`。非归一化格式（如 PaddleOCR-VL 像素坐标，保持纵横比）仍走原推断逻辑，`sy` 回退为 `sx`，兼容不破坏。

换算公式：
```
left   = x0 * (page.width  / 1000)
top    = y0 * (page.height / 1000)
width  = (x1 - x0) * (page.width  / 1000)
height = (y1 - y0) * (page.height / 1000)
```

## 验证

- 后端改动 `python -m py_compile` 全部通过。
- 模型路径校验：pipeline 根 + `models/MFR/unimernet_hf_small_2503` 等关键子目录均命中。
- PDF 路径修复用真实任务数据模拟：旧逻辑 `ValueError`、新逻辑正确解析。
- 坐标偏移用同一文档 8 个真实块交叉验证比例（x≈1.63、y≈1.26 恒定），并在 MinerU 源码确认 [0,1000] 归一化约定。
- 前端 `tsc && vite build` 构建通过。

## 注意事项

- 历史任务的错误 `result.json`（问题 3）不会被覆盖（normalizer 检测到已存在即跳过），需**重新提交文件**走新逻辑；问题 4 的 PDF 预览修复则对历史任务即时生效。
- 以上后端注入逻辑仅在通过 `start_all.py` 启动时生效。若单独直接运行 `python litserve_worker.py`，需自行设置 `MODEL_PATH` / `PADDLEX_HOME` / `MINERU_TOOLS_CONFIG_JSON`。
